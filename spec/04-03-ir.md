# §4.3 Intermediate Representation

The Bliss optimising compiler (Tier 2) uses a **sea-of-nodes SSA IR**
inspired by HotSpot C2 and GraalVM.  Every operation is a node; edges
encode data flow (def-use), control flow, and memory ordering.  The IR
is constructed from macro-expanded CL forms (§4.2) and consumed by
optimisation passes (§4.4) before lowering to machine code (§4.6).

---

## 4.3.1 Requirements

| ID | Requirement |
|----|-------------|
| R4.17 | The IR MUST be in static single-assignment (SSA) form: every value node produces exactly one definition, and dominance properties hold at all times. |
| R4.18 | The IR MUST represent data dependencies, control dependencies, and memory ordering as distinct, typed edge classes. |
| R4.19 | The IR builder MUST produce well-formed IR from any fully macro-expanded CL form, including all special operators defined in ANSI CL §3.1.2.1.2. |
| R4.20 | A verification pass (A4.07) MUST detect violations of SSA dominance, type consistency, and edge well-formedness, and MUST be run after every pass in debug builds. |
| R4.21 | The IR MUST support speculative guards (type checks, bounds checks, nil checks) with associated uncommon-trap metadata so that a failed guard triggers deoptimisation (§4.5) rather than a hard error. |
| R4.22 | Every IR node MUST carry source-position information sufficient to reconstruct a CL source location (file, line, column, macro-expansion depth) for debugger and condition-system use. |

---

## 4.3.2 Data Structure D4.01 — Node Types

### 4.3.2.1 Node Representation

Every node is heap-allocated and referenced by a stable `NodeId`
(a `u32` index into the graph's node arena).

```rust
/// Core node record, stored in Graph::nodes arena.
pub struct Node {
    pub id:          NodeId,
    pub opcode:      Opcode,          // discriminant — see §4.3.2.2
    pub ty:          IRType,          // result type (Bottom for void)
    pub inputs:      SmallVec<[Input; 4]>,   // edges TO this node
    pub source_pos:  SourcePosition,  // §4.3.7
    pub flags:       NodeFlags,       // bitflags: PINNED, GUARD, DEAD, …
    pub aux:         AuxData,         // opcode-specific payload (enum)
}

/// Stable handle into the node arena.
#[derive(Copy, Clone, Eq, PartialEq, Hash)]
pub struct NodeId(pub u32);

bitflags::bitflags! {
    pub struct NodeFlags: u16 {
        const PINNED        = 0x0001; // must not float (side-effecting)
        const GUARD         = 0x0002; // speculative guard node
        const DEAD          = 0x0004; // marked for removal
        const LOOP_HEADER   = 0x0008; // control merge at loop head
        const SAFEPOINT     = 0x0010; // GC safepoint attached
        const COMMUTATIVE   = 0x0020; // inputs may be reordered
    }
}
```

### 4.3.2.2 Opcode Hierarchy

Opcodes are grouped into five categories.  Each opcode specifies the
**number and kinds of inputs** it expects, and whether it produces a
value, has control-flow side effects, or orders memory.

#### Category 1 — Constants & Parameters

| Opcode | Inputs | Output Type | Description |
|--------|--------|-------------|-------------|
| `Param(index)` | control: Start | per-signature | Function parameter |
| `ConstFixnum(i61)` | — | Fixnum | Immediate fixnum |
| `ConstFloat(f32)` | — | SingleFloat | Immediate single-float |
| `ConstChar(u21)` | — | Character | Immediate character |
| `ConstSymbol(SymId)` | — | Symbol | Interned symbol reference |
| `ConstNil` | — | Null | The value NIL |
| `ConstT` | — | Boolean | The value T |
| `ConstHeapObj(HeapRef)` | — | HeapObject | Quoted heap literal |

#### Category 2 — Arithmetic & Logic

All binary arithmetic opcodes take `(lhs, rhs)` data inputs.  Unary
opcodes take a single `val`.

| Sub-group | Opcodes | Output Type |
|-----------|---------|-------------|
| Fixnum arith | `FixnumAdd`, `FixnumSub`, `FixnumMul` | Fixnum |
| Fixnum unary | `FixnumNeg` | Fixnum |
| Fixnum shift | `FixnumShl`, `FixnumShr` (val, count) | Fixnum |
| Float arith | `FloatAdd`, `FloatSub`, `FloatMul`, `FloatDiv` | SingleFloat |
| Generic arith | `GenericAdd`, `GenericSub`, `GenericMul`, `GenericDiv` | T |
| Bitwise | `LogAnd`, `LogOr`, `LogXor` (binary), `LogNot` (unary) | Fixnum |

Fixnum overflow on `FixnumAdd`/`FixnumSub`/`FixnumMul` triggers
an `ArithmeticOverflow` uncommon trap (§4.3.6).

#### Category 3 — Comparison & Type Checks

| Opcode | Inputs | Output | Description |
|--------|--------|--------|-------------|
| `Fixnum{CmpEq,CmpLt,CmpLe}` | lhs, rhs | Boolean | Fixnum `=`, `<`, `<=` |
| `Float{CmpEq,CmpLt}` | lhs, rhs | Boolean | Float `=`, `<` |
| `GenericEq` / `GenericEqual` | lhs, rhs | Boolean | `CL:EQL` / `CL:EQUAL` |
| `TypeCheck` | val | Boolean | Test tag bits against `IRType` |
| `InstanceOf` | val | Boolean | CLOS class membership test |

#### Category 4 — Memory & Object Access

All memory opcodes take a `Memory(mem-state)` input and those that
write produce a new `mem-state` output.  Reads: `Load(base,offset)`,
`Car(cons)`, `Cdr(cons)`, `VecRef(vec,idx)`, `SymbolValue(sym)`.
Writes: `Store(base,offset,val)`, `SetCar(cons,val)`,
`SetCdr(cons,val)`, `VecSet(vec,idx,val)`, `SetSymbolValue(sym,val)`,
`WriteBarrier(obj,val)`.  Allocation: `Alloc(layout)`,
`AllocCons(car,cdr)` — both take mem-state and produce a new object
plus updated mem-state.

#### Category 5 — Control Flow

**Graph endpoints:** `Start` (no inputs; produces initial ctrl+mem),
`Return(ctrl, val, mem)`.

**Branching:** `If(ctrl, cond)` → `TrueProj(If)` / `FalseProj(If)`;
`Jump(ctrl)` — unconditional.

**Merging:** `Region(ctrl…)` — ≥2 control inputs; `Phi(region, val…)`
— one value per Region predecessor.

**Calls:** `Call(target)(ctrl, mem, args…)` / `TailCall(target)` —
produce three projections: `CallResult`, `CallMem`, `CallCtrl`.

**Speculation:** `Guard(ctrl, cond, deopt)` — see §4.3.6;
`UncommonTrap(ctrl, deopt-info)` — deoptimise to interpreter.

**GC / NLX:** `Safepoint(ctrl, mem)`, `Throw(ctrl, condition-obj)`,
`NLXEntry(ctrl)`, `NLXTransfer(ctrl, tag, vals)`.

### 4.3.2.3 Opcode-Specific Auxiliary Data

`AuxData` is an enum carrying per-opcode payload: `ParamIndex(u16)`,
`FixnumImm(i64)`, `FloatImm(f32)`, `CharImm(char)`, `SymbolRef(SymId)`,
`HeapLiteral(HeapRef)`, `AllocLayout(LayoutId)`, `FieldOffset(u32)`,
`CallTarget(FunctionRef)`, `DeoptInfo(DeoptInfoId)`, `PhiWidth(u16)`,
`TypeTag(IRType)`, `ClassRef(ClassId)`, `NLXTag(NLXTagId)`, or `None`.

### 4.3.2.4 IRType — Type Lattice

The IR type system represents the CL type lattice as a compact bitset
plus optional refinements.

```rust
pub struct IRType {
    pub bits:     TypeBits,       // bitset of possible type tags
    pub range:    Option<Range>,  // integer sub-range refinement
    pub class_id: Option<ClassId>,// CLOS class refinement
}
```

`TypeBits` is a `u16` bitflag with one bit per major CL type: `FIXNUM`,
`BIGNUM`, `RATIO`, `SINGLE_FLOAT`, `DOUBLE_FLOAT`, `COMPLEX`,
`CHARACTER`, `CONS`, `NULL`, `SYMBOL`, `STRING`, `VECTOR`, `FUNCTION`,
`INSTANCE`, `OTHER_HEAP`.  `BOTTOM` (0x0000) means void/unreachable;
`TOP` (all bits) means any CL value.  `meet` computes intersection
(bitwise AND), `join` computes union (bitwise OR), with range/class
narrowing where applicable.

## 4.3.3 Data Structure D4.02 — Edge Types

Edges are not stored as first-class objects; they are implicit in each
node's `inputs` array and in a reverse-map (`uses`) maintained by the
`Graph`.  Three edge kinds exist:

| Edge Kind | Stored In | Semantics | Constraint |
|-----------|-----------|-----------|------------|
| **Data (def-use)** | `Input::Data(NodeId)` | Value produced by source, consumed by target | Source MUST dominate target |
| **Control** | `Input::Control(NodeId)` | Execution ordering | Forms a reducible CFG when projected from sea-of-nodes |
| **Memory** | `Input::Memory(NodeId)` | Memory state token (anti-aliased) | Forms a single chain through side-effecting nodes |

```rust
/// A typed edge reference stored in Node::inputs.
#[derive(Copy, Clone, Debug)]
pub enum Input {
    /// Data dependency: this node uses the value of `src`.
    Data(NodeId),
    /// Control dependency: this node executes after `src`.
    Control(NodeId),
    /// Memory ordering: this node's memory view follows `src`.
    Memory(NodeId),
}

impl Input {
    pub fn node_id(&self) -> NodeId {
        match self { Self::Data(n) | Self::Control(n) | Self::Memory(n) => *n }
    }
    pub fn is_data(&self) -> bool    { matches!(self, Self::Data(_)) }
    pub fn is_control(&self) -> bool { matches!(self, Self::Control(_)) }
    pub fn is_memory(&self) -> bool  { matches!(self, Self::Memory(_)) }
}
```

### 4.3.3.1 Input Slot Conventions

Each opcode has a fixed schema declaring which slots are data, control,
or memory.  Representative patterns (used by verifier A4.07):
binary arith = `[Data, Data]`; `Load` = `[Data, Data, Memory]`;
`Store` = `[Data, Data, Data, Memory]`; `If` = `[Control, Data]`;
`Region` = `[Control, Control, …]` (variadic); `Phi` = `[Data(region),
Data, …]`; `Call` = `[Control, Memory, Data, …]` (variadic);
`Return` = `[Control, Data, Memory]`; `Guard` = `[Control, Data, Data]`.

### 4.3.3.2 Use Lists (Reverse Edges)

The `Graph` maintains a `uses: Vec<SmallVec<[UseEdge; 2]>>` array,
indexed by `NodeId`, recording all nodes that consume a given node's
output.  This allows O(1) iteration over users for substitution and
dead-code elimination.

```rust
#[derive(Copy, Clone)]
pub struct UseEdge {
    pub user:      NodeId,   // consuming node
    pub slot:      u8,       // index into user.inputs
}
```

Use lists MUST be kept in sync with `inputs` at all times.  The helper
methods `Graph::replace_input` and `Graph::remove_node` maintain this
invariant.

## 4.3.4 Graph Container

```rust
pub struct Graph {
    pub nodes:      Vec<Node>,                     // arena, indexed by NodeId
    pub uses:       Vec<SmallVec<[UseEdge; 2]>>,   // reverse edge map
    pub start:      NodeId,                        // unique Start node
    pub end:        NodeId,                        // unique Return/Throw merge
    pub deopt_info: Vec<DeoptInfo>,                // table for Guard nodes
    pub source_map: SourceMap,                     // compressed positions
    pub next_id:    u32,                           // monotonic id counter
}
```

Key methods: `add_node(opcode, ty, inputs, src) → NodeId`,
`replace_input(node, slot, new_src)` (updates use lists),
`remove_node(node)` (marks DEAD, removes from uses),
`live_nodes() → Iterator`, `dominators() → DominatorTree`
(Cooper-Harvey-Kennedy algorithm over the projected CFG).

## 4.3.5 IR Builder — Graph Construction from CL Forms

### 4.3.5.1 Overview

The IR builder walks the fully-expanded CL form tree (§4.2) and
produces a sea-of-nodes `Graph`.  It maintains:

- **`ctrl`**: the current control-flow token (`NodeId`).
- **`mem`**: the current memory-state token (`NodeId`).
- **`env`**: a lexical environment mapping CL variable names to
  `NodeId`s of their current SSA definitions.

### 4.3.5.2 Algorithm — Build

The builder is a recursive function with signature:

```text
build(form, env, ctrl, mem) → (value: NodeId, ctrl': NodeId, mem': NodeId)
```

Key form-lowering rules (representative subset):

| CL Form | IR Construction |
|---------|-----------------|
| Literal fixnum/symbol/… | Emit `Const*` node; `ctrl`/`mem` unchanged |
| Lexical variable ref | Return `env.lookup(name)`; `ctrl`/`mem` unchanged |
| Special variable ref | Emit `SymbolValue` with `Memory(mem)` input |
| `IF` | Build test → emit `If` + `TrueProj`/`FalseProj` → build both branches → merge with `Region` + `Phi` for value and memory |
| `LET`/`LET*` | Build each init form, extend env with `name→NodeId`, build body |
| `SETQ` (lexical) | Build value, update `env` mapping (SSA rename, no Store) |
| `SETQ` (special) | Build value, emit `SetSymbolValue` with memory threading |
| Function call | Build args left-to-right, emit `Call` + three projections (`CallResult`, `CallMem`, `CallCtrl`) |
| `TAGBODY`/`GO` | See §4.3.5.3 (loop construction) |
| `BLOCK`/`RETURN-FROM` | Emit `NLXEntry` at block head; `RETURN-FROM` emits `NLXTransfer` |
| `THE` | Build inner form, narrow `IRType`; optionally insert `Guard` |
| `VALUES`/`M-V-BIND` | See §4.3.5.4 (multiple values) |

### 4.3.5.3 Loop Construction (TAGBODY / DO)

Loops are constructed using a **Region** node as the loop header with
back-edge **Phi** nodes for every mutable variable:

1. Create a `Region` node with two control inputs: the entry edge and
   a placeholder for the back-edge.
2. For each variable live across the loop, create a `Phi` with one
   input from before the loop and one placeholder for the back-edge
   value.
3. Build the loop body, threading `ctrl` and `mem` through.
4. At `GO` to the header tag, patch the back-edge inputs of the
   Region and all Phis.
5. Mark the Region with `LOOP_HEADER` flag.

### 4.3.5.4 Multiple Values

`VALUES` produces a `ValuesNode` with N data inputs.
`MULTIPLE-VALUE-BIND` destructures via `ValuesExtract(index)` projection
nodes.  The type system tracks multiple-value arity in `IRType`.

## 4.3.6 Speculative Guards & Uncommon Traps

### 4.3.6.1 Guard Nodes

A `Guard` node represents a speculative assumption inserted by the
compiler based on profiling data or declared types.  It has:

- **Control input**: where in the control flow it executes.
- **Condition input**: a boolean node; if false, the guard fails.
- **Deopt input**: an `UncommonTrap` node describing how to resume in
  the interpreter.

```text
  Guard(ctrl, cond=TypeCheck(x, Fixnum),
        deopt=UncommonTrap(reason=TypeMismatch, bci=42))
```

If the condition is true, execution continues on the Guard's output
control edge.  If false, control transfers to `UncommonTrap`, which
reconstructs the interpreter frame and resumes at the bytecode index
(or tree-walk position) recorded in `DeoptInfo`.

### 4.3.6.2 DeoptInfo Table

```rust
pub struct DeoptInfo {
    pub reason:      DeoptReason,
    pub source_pos:  SourcePosition,      // CL source location
    pub frame_state: Vec<FrameSlot>,      // values to reconstruct
    pub caller:      Option<DeoptInfoId>, // inlined caller chain
}

pub enum DeoptReason {
    TypeMismatch,
    BoundsCheckFailed,
    NilCheck,
    ClassHierarchyChanged,
    DivisionByZero,
    ArithmeticOverflow,
    Unreached,                // code path never taken in profiling
}

pub struct FrameSlot {
    pub kind:  SlotKind,    // Local, Stack, SpecialBinding
    pub name:  Option<SymId>,
    pub value: NodeId,      // IR node producing the live value
}
```

### 4.3.6.3 Guard Strength Reduction

During optimisation, redundant guards are eliminated:

- **Dominating guard**: if guard G1 dominates G2 and both check the
  same condition, G2 is removed.
- **Type-narrowing**: after a TypeCheck guard succeeds, downstream
  uses of the guarded value are given a narrowed `IRType`, enabling
  specialised arithmetic opcodes.
- **Guard motion**: guards MAY be hoisted out of loops when the
  checked condition is loop-invariant.

## 4.3.7 Source Position Tracking

Every IR node carries a `SourcePosition` recording its origin:

```rust
#[derive(Copy, Clone, Default)]
pub struct SourcePosition {
    pub file_id:    u16,        // index into SourceMap::files
    pub line:       u32,        // 1-based line number
    pub column:     u16,        // 0-based column
    pub macro_depth: u8,        // 0 = top-level; >0 = inside expansion
    pub inlined_at: Option<SourcePositionId>, // for inlined call sites
}
```

The `Graph::source_map` stores a compressed table of file names and
a pool of `SourcePosition` records.  Duplicate positions are interned.

**Invariant:** After inlining, the `inlined_at` chain MUST correctly
reflect the full call stack from the inlined callee back to the root
compilation unit.

## 4.3.8 Algorithm A4.07 — IR Verification

The verification pass runs after every optimisation pass in debug
builds (`cfg!(debug_assertions)`) and is invocable on-demand in
release builds via the `--verify-ir` flag.

### 4.3.8.1 Checks Performed

| # | Check | Severity |
|---|-------|----------|
| V1 | **No dangling references**: every `NodeId` in inputs/uses refers to a live (non-DEAD) node in the graph arena. | Fatal |
| V2 | **Use-list consistency**: for every input edge (node N, slot S, target T), `uses[T]` contains `UseEdge { user: N, slot: S }`, and vice-versa. | Fatal |
| V3 | **SSA dominance**: for every `Data` input, the source node dominates the consumer in the projected CFG. | Fatal |
| V4 | **Phi placement**: every `Phi` node's input[0] MUST be a `Region`, and the number of value inputs MUST equal the Region's control input count. | Fatal |
| V5 | **Type consistency**: every `Data` input's `IRType` MUST be a subtype of the consuming opcode's declared input type for that slot. | Error |
| V6 | **Control edge integrity**: every non-Start node has exactly one control input (except `Region`, which has ≥ 2). | Fatal |
| V7 | **Memory chain**: memory-producing nodes form a single chain per memory partition; no memory-state node has zero or > 1 uses (except at merge points via Phi). | Error |
| V8 | **Guard well-formedness**: every `Guard` node has exactly one `UncommonTrap` deopt successor, and its `DeoptInfo` index is valid. | Error |
| V9 | **Source position**: every node has a non-default `SourcePosition` (warning only; not fatal). | Warning |
| V10 | **Input slot schema**: each node's inputs match the count and kinds (Data/Control/Memory) declared by its opcode's schema (§4.3.3.1). | Fatal |

### 4.3.8.2 Algorithm Pseudocode

```text
function verify(graph: Graph) → Vec<VerifyError>:
    errors = []
    dom_tree = graph.dominators()  // Cooper-Harvey-Kennedy algorithm

    for node in graph.live_nodes():
        // V1: all input NodeIds refer to live nodes
        // V2: for each input (node, slot, target), uses[target] contains
        //     the matching UseEdge, and vice-versa
        // V3: for non-Phi data inputs, source dominates consumer
        //     (checked via dom_tree)
        // V4: Phi input[0] must be Region; value-input count == Region
        //     control-input count
        // V5: each data input's IRType ⊆ opcode schema's declared type
        // V6: control-input count: Start=0, Region≥2, all others=1
        // V10: input count and kinds match opcode_schema()

    // V7: walk memory chain — each mem-producing node has exactly one
    //     user (except Phi merges); detect orphan or forked chains
    // V8: each Guard's DeoptInfo index is within bounds

    return errors
```

### 4.3.8.3 Error Handling

- **Fatal** errors cause an immediate panic in debug builds and log an
  error + abort compilation of the current function in release builds.
  The function falls back to interpreter execution.
- **Error** level issues are logged and the function is marked as
  unoptimisable (falls back to baseline, §4.4).
- **Warning** level issues are logged only; compilation continues.

## 4.3.9 Serialisation & Pretty-Printing

### 4.3.9.1 Text Format

For debugging and test assertions, the IR has a stable text format:

```text
Graph "MY-FUNCTION" (nodes=14)
  n0: Start                              ;; @file.lisp:10:0
  n1: Param(0) : Fixnum <- [ctrl:n0]     ;; @file.lisp:10:5
  n2: Param(1) : Fixnum <- [ctrl:n0]     ;; @file.lisp:10:7
  n3: FixnumAdd : Fixnum <- [data:n1, data:n2]  ;; @file.lisp:11:3
  n4: Return <- [ctrl:n0, data:n3, mem:n0.mem]   ;; @file.lisp:11:3
```

Format: `n<id>: <Opcode>(<aux>)? (: <Type>)? (<- [<edge-kind>:n<id>, ...])?  ;; @<source>`

### 4.3.9.2 Binary Serialisation

For IR caching across compilation sessions, the graph MAY be serialised
to a compact binary format: magic (`BSIR`, 4 bytes), version (2 bytes),
node count (4 bytes), then for each node: opcode (2), type (4),
input-count (1), inputs (5×N: kind u8 + node_id u32), variable-length
aux, and packed source_pos (8).  Followed by length-prefixed deopt
table and source map.  Binary IR is NOT a stable ABI; the version MUST
be bumped on any layout change and readers MUST reject unknown versions.

## 4.3.10 Concurrency & Configuration

IR graphs are single-owner, single-writer; they belong to the
compilation thread that created it and MUST NOT be shared across
threads.  Inlining clones the callee's graph into the caller's.

| Knob | Default | Description |
|------|---------|-------------|
| `BLISS_VERIFY_IR` | `true` in debug, `false` in release | Run verification after every pass |
| `BLISS_IR_DUMP` | `false` | Dump text IR to stderr after each pass |
| `BLISS_IR_DUMP_FILTER` | `*` | Glob filter for function names to dump |
| `BLISS_IR_CACHE` | `false` | Enable binary serialisation cache |

| Test | Method | Coverage |
|------|--------|----------|
| IR builder round-trip | Build IR from CL forms, verify, pretty-print, compare against golden files | R4.19 |
| Verifier positive | Construct intentionally broken graphs, assert verifier catches each violation (V1–V10) | R4.20 |
| Verifier negative | Construct valid graphs, assert verifier passes with zero errors | R4.20 |
| Guard deopt | Build IR with guards, simulate guard failure, check DeoptInfo reconstruction | R4.21 |
| Source position | Build IR from multi-line CL with macros, assert every node has correct source position and macro depth | R4.22 |
| Text serialisation | Round-trip: build → pretty-print → parse → pretty-print, assert identical | R4.17 |
| Binary serialisation | Round-trip: build → serialise → deserialise → verify, assert graph equivalence | R4.17 |
| Edge consistency | Fuzz: random graph mutations via `replace_input`, assert use-lists remain consistent after each | R4.18 |
