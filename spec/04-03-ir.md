# §4.3 Intermediate Representation

The EGCL optimising compiler (Tier 2) uses a **block-based SSA IR** in the
Cranelift / TurboFan-lite lineage: a control-flow graph of basic blocks, where
data flow is carried by SSA values (instruction results and typed **block
parameters**, which replace φ-nodes), control flow is carried by explicit
**terminator** edges that pass block-argument lists, and effect ordering is the
program order of effectful instructions within a block. The IR is constructed
from the macroexpanded bytecode (§4.4, the cross-tier coordinate system) and consumed by optimisation passes (§4.5)
before lowering to machine code (§4.7).

This flavour was chosen (over sea-of-nodes) because deoptimisation metadata and
OSR entry (§4.6, §4.10) are materially easier to build, schedule, and verify when
a `FrameState` attaches to a concrete instruction and names ordinary SSA values,
than when it must be reconstructed from floating nodes and a memory-token chain.
The cost is some global code-motion freedom, recovered by explicit LICM/GVN
passes (§4.5). Consequently this IR has **no** memory-state SSA tokens, **no**
floating/pinned Region/Phi machinery, and **no** projected CFG: the CFG is
primary.

---

## 4.3.1 Requirements

| ID | Requirement |
|----|-------------|
| R4.17 | The IR MUST be in static single-assignment (SSA) form: every value has exactly one definition (an instruction result or a block parameter), and SSA dominance holds at all times (a value's definition dominates every use). |
| R4.18 | The IR MUST be a CFG of basic blocks. Data flow MUST be SSA values; control flow MUST be explicit terminator edges carrying block-argument lists (block parameters replace φ-nodes); effect ordering MUST be the program order of effectful instructions within a block, disambiguated by alias analysis. There MUST be no implicit fall-through between blocks, and every block MUST end in exactly one terminator. |
| R4.19 | The IR builder MUST produce well-formed IR from any fully macro-expanded CL form, including all special operators defined in ANSI CL §3.1.2.1.2. |
| R4.20 | A verification pass (A4.07) MUST detect violations of SSA dominance, block-parameter arity/type agreement, terminator well-formedness, type consistency, and effect ordering, and MUST be run after every pass in debug builds. |
| R4.21 | The IR MUST support speculative guards (type checks, bounds checks, nil checks) that carry a `FrameState` (§4.10 D4.15) and a deopt reason, so that a failed guard triggers deoptimisation (§4.6) rather than a hard error. |
| R4.22 | Every instruction and block parameter MUST carry source-position information sufficient to reconstruct a CL source location (file, line, column, macro-expansion depth) for debugger and condition-system use. |

## 4.3.2 Data Structure D4.01 — Functions, Blocks, Instructions, Values

### 4.3.2.1 Arenas & Handles

An IR function is four arenas plus a layout. Handles are dense `u32` indices;
they are stable for the function's lifetime.

```rust
/// A block-based SSA function.
pub struct Function {
    pub blocks:     Vec<BlockData>,   // arena, indexed by Block
    pub insts:      Vec<InstData>,    // arena, indexed by Inst
    pub values:     Vec<ValueData>,   // arena, indexed by Value
    pub entry:      Block,            // unique entry block
    pub layout:     Layout,           // block order + per-block instruction order
    pub source_map: SourceMap,        // §4.3.7
    pub signature:  Signature,        // parameter & return types
}

#[derive(Copy, Clone, Eq, PartialEq, Hash)] pub struct Block(pub u32);
#[derive(Copy, Clone, Eq, PartialEq, Hash)] pub struct Inst(pub u32);
#[derive(Copy, Clone, Eq, PartialEq, Hash)] pub struct Value(pub u32);
```

`Layout` holds the intrusive doubly-linked orders — the sequence of blocks and,
within each block, the sequence of instructions ending in the terminator — so
insertion/removal during optimisation is O(1) and does not renumber handles.

### 4.3.2.2 Blocks

```rust
pub struct BlockData {
    /// Typed block parameters — the SSA form of φ-nodes. The entry block's
    /// parameters are the function parameters; every other block's parameters
    /// receive their values from predecessors' terminator block-argument lists.
    pub params: SmallVec<[Value; 4]>,
}
```

A block's instruction list and terminator live in `Layout`. A block is
**well-formed** (V6) iff its last instruction is a terminator and no earlier
instruction is one.

### 4.3.2.3 Values

```rust
pub struct ValueData {
    pub def:  ValueDef,
    pub ty:   IRType,               // CL type lattice — §4.3.2.6
    pub repr: ValueRepresentation,  // machine representation — §4.10 D4.16
}

pub enum ValueDef {
    /// The `num`-th result of an instruction.
    Result { inst: Inst, num: u16 },
    /// The `num`-th parameter of a block.
    Param  { block: Block, num: u16 },
}
```

`ty` answers "what CL object is this"; `repr` answers "in what physical form"
(tagged EgclVal, unboxed fixnum, unboxed f32/f64 — §4.10). The two are
orthogonal: box/unbox instructions change `repr` while preserving `ty`.

### 4.3.2.4 Instructions

```rust
pub struct InstData {
    pub opcode:     Opcode,                 // §4.3.2.5
    pub args:       SmallVec<[Value; 3]>,   // SSA value operands (data edges)
    pub results:    SmallVec<[Value; 1]>,   // 0..n SSA results
    pub aux:        AuxData,                // opcode-specific payload
    pub source_pos: SourcePosition,         // §4.3.7
    pub flags:      InstFlags,
    /// Successor edges — non-empty only for terminators. Each names a block and
    /// the block-argument list passed to that block's parameters.
    pub targets:    SmallVec<[BlockCall; 2]>,
    /// Present on guards and any deoptimising instruction (R4.21): the
    /// interpreter state to reconstruct on a failed guard (§4.10 D4.15).
    pub frame_state: Option<FrameStateId>,
}

/// A control-flow edge target: a successor block plus the arguments bound to
/// that block's parameters on this edge.
pub struct BlockCall {
    pub block: Block,
    pub args:  SmallVec<[Value; 4]>,
}

bitflags::bitflags! {
    pub struct InstFlags: u16 {
        const EFFECTFUL  = 0x0001; // observable side effect; program order fixed
        const GUARD      = 0x0002; // deoptimising guard (carries a FrameState)
        const SAFEPOINT  = 0x0004; // GC safepoint attached
        const TERMINATOR = 0x0008; // ends its block; has successor `targets`
        const CALL       = 0x0010; // may transfer control / clobber caller-saves
        const COMMUTATIVE = 0x0020;// operands may be reordered (for GVN)
    }
}
```

Instructions default to **pure**: a pure instruction has no ordering constraint
beyond SSA data dependence and MAY be reordered, hoisted, GVN'd, or
rematerialised (§4.10 A4.13). An **EFFECTFUL** instruction (store, mutable load,
call, allocation, guard, safepoint, symbol-value access) keeps its program order
within its block; cross-block order follows the CFG. There is no separate memory
edge — ordering among effectful instructions is their layout order, refined by
alias analysis (§4.5). This replaces the sea-of-nodes memory-token chain.

### 4.3.2.5 Opcode Catalogue

Opcodes fall into five categories. Categories 1–4 are ordinary value-producing
instructions; Category 5 is control flow (terminators + guards).

#### Category 1 — Constants & Parameters

| Opcode | Results | Result Type | Description |
|--------|---------|-------------|-------------|
| `ConstFixnum(i61)` | 1 | Fixnum | Immediate fixnum |
| `ConstFloat(f32)` | 1 | SingleFloat | Immediate single-float |
| `ConstChar(u21)` | 1 | Character | Immediate character |
| `ConstSymbol(SymId)` | 1 | Symbol | Interned symbol reference |
| `ConstNil` | 1 | Null | The value NIL |
| `ConstT` | 1 | Boolean | The value T |
| `ConstHeapObj(HeapRef)` | 1 | HeapObject | Quoted heap literal |

Function parameters are the **entry block's parameters** (not an opcode).

#### Category 2 — Arithmetic & Logic

Binary arithmetic takes `(lhs, rhs)`; unary takes `val`.

| Sub-group | Opcodes | Result Type |
|-----------|---------|-------------|
| Fixnum arith | `FixnumAdd`, `FixnumSub`, `FixnumMul`, `FixnumDiv` | Fixnum |
| Fixnum rem/mod | `FixnumRem`, `FixnumMod` | Fixnum |
| Fixnum unary | `FixnumNeg` | Fixnum |
| Fixnum shift | `FixnumShl`, `FixnumShr` (val, count) | Fixnum |
| Float arith | `FloatAdd`, `FloatSub`, `FloatMul`, `FloatDiv` | SingleFloat |
| Generic arith | `GenericAdd`, `GenericSub`, `GenericMul`, `GenericDiv` | T |
| Bitwise | `LogAnd`, `LogOr`, `LogXor` (binary), `LogNot` (unary) | Fixnum |
| Representation | `BoxFixnum`, `UnboxFixnum`, `BoxFloat`, `UnboxFloat`, `WidenI32` | — |

`FixnumAdd`/`FixnumSub`/`FixnumMul` are **GUARD**-flagged when a range proof does
not rule out overflow: overflow deoptimises via an `ArithmeticOverflow` reason.
`FixnumDiv`/`FixnumRem`/`FixnumMod` deoptimise on a zero divisor
(`DivisionByZero`). `FixnumDiv` = `CL:TRUNCATE`; `FixnumRem` = `CL:REM`;
`FixnumMod` = `CL:MOD`. Representation opcodes (R4.61) are the *only* way `repr`
changes; they are pure and rematerialisable (§4.10 D4.17).

#### Category 3 — Comparison & Type Checks

| Opcode | Args | Result | Description |
|--------|------|--------|-------------|
| `Fixnum{CmpEq,CmpLt,CmpLe,CmpGt,CmpGe}` | lhs, rhs | Boolean | Fixnum `=`,`<`,`<=`,`>`,`>=` |
| `Float{CmpEq,CmpLt}` | lhs, rhs | Boolean | Float `=`, `<` |
| `GenericEq` / `GenericEqual` | lhs, rhs | Boolean | `CL:EQL` / `CL:EQUAL` |
| `TypeCheck` | val | Boolean | Test tag bits against an `IRType` (aux) |
| `InstanceOf` | val | Boolean | CLOS class membership test |

A `TypeCheck` (or any Boolean) feeds a `Guard` or a `Brif` (Category 5).

#### Category 4 — Memory & Object Access (effectful unless proven immutable)

Reads: `Load(base, offset)`, `Car(cons)`, `Cdr(cons)`, `VecRef(vec, idx)`,
`SymbolValue(sym)`. Writes: `Store(base, offset, val)`, `SetCar(cons, val)`,
`SetCdr(cons, val)`, `VecSet(vec, idx, val)`, `SetSymbolValue(sym, val)`,
`WriteBarrier(obj, val)`. Allocation: `Alloc(layout)`, `AllocCons(car, cdr)`.

A load from provably immutable memory (e.g. a `cons` known unmutated in scope)
MAY be marked pure and thus hoistable/GVN-able; otherwise loads are EFFECTFUL and
ordered by program order and alias analysis (§4.5). Writes are always EFFECTFUL.

**Write-barrier insertion:** `WriteBarrier` is **not** emitted by the builder. A
dedicated pass (after optimisation, before codegen, §4.5) inserts a
`WriteBarrier` immediately after every `Store`/`SetCar`/`SetCdr`/`VecSet`/
`SetSymbolValue` whose stored value may be a heap pointer (its `IRType` intersects
a heap tag). The barrier follows the GC protocol (§3) and lowers (§4.7) to the
GC-specific sequence (card marking, SATB append, …).

#### Category 5 — Control Flow (Terminators & Guards)

Every block ends in exactly one **terminator** (R4.18). Terminators carry
`targets` (BlockCalls); non-terminators never do.

| Opcode | Kind | Targets | Description |
|--------|------|---------|-------------|
| `Invoke(target)` | terminator | 2 | Call with normal target[0] and exceptional target[1]; normal results are edge-local. |
| `Jump` | terminator | 1 | Unconditional branch; passes block args. |
| `Brif(cond)` | terminator | 2 | `cond`-true → target[0], false → target[1]. |
| `BrTable(idx)` | terminator | n+1 | Indexed branch (default last); for `CASE`. |
| `Return(vals…)` | terminator | 0 | Return values to caller. |
| `TailCall(target)` | terminator | 0 | Tail call; args are value operands. |
| `Throw` | terminator | 0 | Signal / non-local exit (condition object arg). |
| `NlxTransfer(tag)` | terminator | 0 | `RETURN-FROM`/`GO`/`THROW` transfer. |
| `Trap(reason)` | terminator | 0 | Unconditional deoptimise (carries FrameState). |

**Guards** are *not* terminators — they are EFFECTFUL, GUARD-flagged instructions
in the middle of a block that deoptimise as a runtime side-exit rather than a CFG
edge, keeping the CFG free of cold deopt blocks:

```text
  guard TypeCheck(x, Fixnum)  frame_state=fs42   ;; if false → deopt (§4.6 A4.04)
```

`Call` is an ordinary EFFECTFUL/CALL instruction (not a terminator); it produces
its result value(s) and returns to the next instruction. `MULTIPLE-VALUE` results
are modelled as multi-result instructions (§4.3.5.4).

`Invoke` makes the exceptional continuation explicit. It carries EFFECTFUL,
CALL and SAFEPOINT flags, a call target, and a pre-call `FrameState`. Its two
successor blocks are distinct. An Invoke result exists only on successful
completion: it can appear only among that instruction's normal edge arguments.
Further uses name the receiving block parameter. Exceptional edge arguments
name pre-call values; the pending transfer itself is execution-owned runtime
state. Neither an exceptional argument nor the pre-call FrameState can name the
normal result. The pre-call snapshot does not authorize replay of a failed call.

Both successors participate in dominance, reachability and liveness. The verifier
checks edge-local definitions separately from ordinary instruction dominance.
`Function::make_call_exceptional` splits a bytecode-built Call's block and
projects its result through normal block parameters, including downstream frame
states. Inlining creates the cloned result before translating normal edge args.
During ABI migration the existing builder still emits ordinary Call; Invoke
machine emission remains unsupported until native landing maps are available.

### 4.3.2.6 IRType — Type Lattice (D4.08)

The IR type system represents the CL type lattice as a compact bitset plus
refinements.

```rust
pub struct IRType {
    pub bits:     TypeBits,        // bitset of possible type tags
    pub range:    Option<Range>,   // integer sub-range refinement
    pub class_id: Option<ClassId>, // CLOS class refinement
}
```

`TypeBits` is a `u16` with one bit per major CL type: `FIXNUM`, `BIGNUM`, `RATIO`,
`SINGLE_FLOAT`, `DOUBLE_FLOAT`, `COMPLEX`, `CHARACTER`, `CONS`, `NULL`, `SYMBOL`,
`STRING`, `VECTOR`, `FUNCTION`, `INSTANCE`, `OTHER_HEAP`. `BOTTOM` (0x0000) is
void/unreachable; `TOP` (all bits) is any CL value. `meet` = intersection,
`join` = union, with range/class narrowing. The `range` refinement is load-bearing
for T2 (§4.10): a counted loop whose index is proved `FIXNUM[0, n)` drops its
overflow guard. This is the lattice R4.31 (§4.5) propagates.

### 4.3.2.7 Auxiliary Data

`AuxData` carries per-opcode payload: `FixnumImm(i64)`, `FloatImm(f32)`,
`CharImm(char)`, `SymbolRef(SymId)`, `HeapLiteral(HeapRef)`, `AllocLayout(LayoutId)`,
`FieldOffset(u32)`, `CallTarget(FunctionRef)`, `TypeTag(IRType)`, `StringLayout`,
`ClassRef(ClassId)`, `NLXTag(NLXTagId)`, `DeoptReason(DeoptReason)`,
`JumpTable(JumpTableId)`, or `None`. `StringLayout` is a representation proof,
not merely `TypeTag(STRING)`: it promises one of the directly addressable simple
string layouts and therefore remains distinct from the broader CL type.

## 4.3.3 Data Structure D4.02 — Edges

There are exactly two structural edge kinds; the sea-of-nodes "memory" edge is
gone (§4.3.2.4).

| Edge Kind | Stored In | Semantics | Constraint |
|-----------|-----------|-----------|------------|
| **Data (def-use)** | `InstData.args`, `BlockCall.args` | An SSA value produced by its definition, consumed here | Definition MUST dominate the use (SSA, R4.17) |
| **Control** | `InstData.targets` (terminators only) | Successor block + block-argument list | Target block exists; arg count = target's `params.len()` (V4); CFG reducible for natural loops |

The `Function` maintains a reverse **use map** (`uses: SecondaryMap<Value, …>`)
listing, for each value, the `(inst, operand-slot)` and `(block-call, arg-slot)`
sites that consume it, for O(1) substitution and DCE. Predecessor lists per block
are derived from terminator targets and cached.

```rust
pub enum ValueUse {
    InstArg  { inst: Inst,   slot: u16 },
    BlockArg { inst: Inst,   target: u8, slot: u16 }, // in a terminator's BlockCall
}
```

Use lists and predecessor lists MUST stay in sync with `args`/`targets`; the
helpers `replace_value`, `remove_inst`, and `replace_block_call` maintain them.

## 4.3.4 Dominance & CFG Utilities

Because the CFG is primary, dominance is computed directly on it — no projection.

Key methods: `append_inst(block, opcode, args, aux, src) → Inst`,
`append_param(block, ty, repr) → Value`, `set_terminator(block, term)`,
`replace_value(old, new)`, `remove_inst(inst)`, `preds(block) → &[Block]`,
`succs(block) → impl Iterator`, `dominators() → DominatorTree`
(Cooper–Harvey–Kennedy over the CFG), `loop_forest() → LoopForest`
(natural loops via back-edge analysis, for LICM §4.5).

## 4.3.5 IR Builder — Construction from CL Forms

### 4.3.5.1 Overview

The builder's input is a `egcl_rt::bytecode::BytecodeFunction` (§4.4) — the same
bytecode T0 interprets and T1 compiles, so every IR instruction is anchored to a
bytecode index (`bcp`) and deopt/OSR resume coordinates line up by construction
(§4.10). The builder **abstractly interprets** the bytecode, producing SSA
**directly in block-parameter form** via the Braun et al. algorithm ("Simple and
Efficient Construction of Static Single Assignment Form"). Two kinds of state
become SSA `Value`s:

- **Operand-stack slots** — the stack-based bytecode's push/pop are modelled as a
  compile-time stack of `Value`s; at a basic-block boundary (a jump target) the
  live operand-stack entries become that block's leading parameters. This is the
  standard stack-bytecode-to-SSA technique.
- **Local slots** — each `LoadLocal`/`StoreLocal` reads/writes the current SSA
  definition of that lexical slot via `read_var`/`write_var` below.

Block boundaries are the bytecode's control-flow targets: a `Br`/`BrIfFalse`/
`BrIfTrue`/`Go` target and each fall-through successor start a block; the
terminator carries the block-argument lists. The builder maintains:

- **`current`**: the block instructions are currently appended to.
- **`var_def: Map<(Block, SlotId), Value>`** — the current SSA definition of each
  local (and operand-stack) slot per block.
- **`sealed: Set<Block>`** — a block is sealed once all its predecessors are
  known; unsealed blocks (loop headers mid-build) may still gain predecessors.

Two primitives drive the on-the-fly SSA construction:

```text
write_var(var, block, value):   var_def[(block, var)] = value

read_var(var, block) → value:
  if (block, var) in var_def:      return var_def[(block, var)]
  if block not sealed:             // may gain more preds later
      p = new block param on block; record it as an INCOMPLETE phi for var
      write_var(var, block, p);    return p
  if block has one pred:           return read_var(var, pred)
  else:                            // multiple preds: create a phi (block param)
      p = new block param on block; write_var(var, block, p)
      for each pred: add read_var(var, pred) to pred's terminator BlockCall→block
      return try_remove_trivial_phi(p)
```

`try_remove_trivial_phi` collapses a block parameter all of whose incoming
arguments are the same value (or itself) back to that value, keeping the SSA
minimal. Sealing a loop header resolves its incomplete phis by filling in the
back-edge arguments.

### 4.3.5.2 Construct-Lowering Rules (representative subset)

The builder consumes bytecode, but bytecode is a faithful lowering of CL forms,
so the recognised bytecode patterns correspond one-to-one to the source
constructs below; the table gives the IR shape produced for each (identified by
its originating form for readability).

| CL Form (bytecode pattern) | IR Construction |
|---------|-----------------|
| Literal fixnum/symbol/… | Append `Const*`; `current` unchanged |
| Lexical variable ref | `read_var(var, current)` |
| Special variable ref | Append `SymbolValue` (EFFECTFUL) |
| `IF` | Build test; `Brif(cond)` to `then`/`else` blocks; build both; both `Jump` to a `join` block whose parameter is the merged value |
| `LET`/`LET*` | Build each init, `write_var` the binding, build body |
| `SETQ` (lexical) | Build value, `write_var(var, current, value)` (pure SSA rename) |
| `SETQ` (special) | Build value, append `SetSymbolValue` (EFFECTFUL) |
| Function call | Build args left-to-right (EGCL guarantees L-to-R; ANSI leaves it unspecified), append `Call`; result is the instruction's value |
| `TAGBODY`/`GO` | Each tag is a block; `GO` is a `Jump`; see §4.3.5.3 |
| `BLOCK`/`RETURN-FROM` | Block exit is a `join` block; a lexical `RETURN-FROM` is a `Jump` to it passing the value; a captured (escaping) one lowers to `NlxTransfer` |
| `THE` | Build inner form; narrow its `IRType`; insert a `Guard` if the narrowing is speculative |
| `PROGN`/`LOCALLY` | Build sub-forms in sequence; value is the last |
| `FLET`/`LABELS` | `Alloc` closure objects for locals, extend env, build body |
| `CATCH`/`THROW` | `CATCH`: append runtime catch-frame setup `Call`; `THROW`: `NlxTransfer` |
| `UNWIND-PROTECT` | Build protected form; register cleanup via runtime `Call`; cleanup built as a closure |
| `PROGV` | Runtime `progv-bind` `Call`; build body; `progv-unbind` `Call` |
| `MULTIPLE-VALUE-CALL` / `M-V-BIND` / `VALUES` | Multi-result instructions; see §4.3.5.4 |

`MACROLET`, `SYMBOL-MACROLET`, and `EVAL-WHEN` MUST be fully expanded by §4.2 and
have no lowering rule; encountering one is a compilation error.

### 4.3.5.3 Loop Construction (TAGBODY / DO)

A loop is built as a **header block with parameters** for each loop-carried
variable — the block-parameter analogue of Region+Phi:

1. Create the header block; leave it **unsealed** (the back-edge predecessor is
   not yet built).
2. `Jump` to the header from the loop entry, passing the pre-loop values as the
   header's initial block arguments.
3. Build the body from the header; `read_var` on a loop variable in an unsealed
   header creates an incomplete phi (a header parameter).
4. `GO`/back-edge lowers to a `Jump` back to the header passing the updated
   loop-carried values.
5. **Seal** the header: fill each incomplete phi's back-edge argument and remove
   any that became trivial.

The result is identical in effect to the old Region/Phi loop, without the
placeholder-patching step, and the header block is a natural-loop header for LICM.

### 4.3.5.4 Multiple Values

`VALUES` produces a multi-result instruction; `MULTIPLE-VALUE-BIND` consumes its
results positionally. Arity is tracked so a values-producing instruction feeding a
single-value context truncates/pads per CL rules.

## 4.3.6 Speculative Guards & Deoptimisation Metadata

### 4.3.6.1 Guard Instructions

A `Guard` is a speculative assumption inserted from profiling (§4.9) or declared
types. It is an EFFECTFUL, GUARD-flagged instruction with:

- either a **condition** operand (a Boolean value, e.g. `TypeCheck(x, Fixnum)`),
  or a checked value plus an auxiliary proof kind (for example `StringLayout`),
- an optional result representing the checked value refined by that proof, and
- a **`FrameState`** (§4.10 D4.15) plus a `DeoptReason` describing how to resume
  in the interpreter if the condition or proof fails.

Consumers of a value proof use the guard's refined result, not its unchecked
operand. Guard elimination MUST forward the removed guard's refined result to
the corresponding result of a dominating equivalent guard.

```text
  guard TypeCheck(x, Fixnum)  reason=TypeMismatch  frame_state=fs42
```

If the condition holds, execution falls through to the next instruction. If it
fails, control transfers to the deopt handler (§4.6 A4.04), which reconstructs the
interpreter frame from the `FrameState` and resumes at its `bcp`. The frame-state
model, its cross-pass **preservation invariant**, and rematerialisation are
specified in §4.10; this chapter's obligation (R4.21) is that every guard *carry*
a valid `FrameState`.

A representation-refining guard MAY return an SSA identity for its checked
operand. Raw layout operations consume that identity, making their dependence on
the proof explicit. If post-inlining guard elimination removes a dominated guard,
uses of its refined result are forwarded to the dominating guard's refined result
(never to the unchecked input).

### 4.3.6.2 Frame State (reference)

The deopt frame-state structure (`FrameState`, `FrameScope`, `ValueSource`) and
the `DeoptReason` enum are defined once, in §4.10 D4.15 and §4.6 D4.10
respectively. §4.3 references them by `FrameStateId` (an index into
`Function`-owned frame-state table) rather than redefining them. Each
`ValueSource::Value` names an SSA `Value`; after register allocation (§4.7) each
is replaced by a physical `Location` (register / stack slot / constant) in the
emitted metadata (§4.10 A4.14). Values named only by frame states are
**deopt-live** and governed by §4.10 R4.60 — passes MUST NOT orphan them.

### 4.3.6.3 Guard Strength Reduction

During optimisation (§4.5), redundant guards are eliminated:

- **Dominating guard**: if guard G1 dominates G2 and both check the same
  condition on the same value, G2 is removed (R4.37).
- **Type narrowing**: after a `TypeCheck` guard succeeds, dominated uses of the
  guarded value are given the narrowed `IRType`, enabling specialised opcodes and
  representation changes.
- **Guard hoisting**: a guard whose condition is loop-invariant MAY be hoisted to
  the loop preheader (§4.10 R4.63), guarding once per loop entry instead of per
  iteration; the hoisted guard's `FrameState` records the pre-narrowing source.

## 4.3.7 Source Position Tracking

Every instruction and block parameter carries a `SourcePosition`:

```rust
#[derive(Copy, Clone, Eq, PartialEq, Hash, Default)]
pub struct SourcePositionId(pub u32);

#[derive(Copy, Clone, Default)]
pub struct SourcePosition {
    pub file_id:     u16,        // index into SourceMap::files
    pub line:        u32,        // 1-based
    pub column:      u16,        // 0-based
    pub macro_depth: u8,         // 0 = top-level; >0 = inside expansion
    pub inlined_at:  Option<SourcePositionId>, // for inlined call sites
}
```

`Function::source_map` interns file names and `SourcePosition` records.

**Invariant:** After inlining, the `inlined_at` chain MUST reflect the full call
stack from the inlined callee back to the root compilation unit — the same chain
the `FrameScope` stack (§4.10 R4.67) uses to un-inline on deopt.

---

## 4.3.8 Algorithm A4.07 — IR Verification

Runs after every optimisation pass in debug builds (`cfg!(debug_assertions)`) and
on demand via `--verify-ir`.

### 4.3.8.1 Checks

| # | Check | Severity |
|---|-------|----------|
| V1 | **No dangling handles**: every `Value`/`Block`/`Inst` referenced in args, targets, params, or uses is live in its arena. | Fatal |
| V2 | **Use-list & pred-list consistency**: for every data use and every terminator BlockCall arg, the reverse maps agree in both directions; each block's predecessor list equals the set of blocks whose terminator targets it. | Fatal |
| V3 | **SSA dominance**: for every value operand, its definition dominates the use; for a block-call argument, the definition dominates the terminator. | Fatal |
| V4 | **Block-parameter agreement**: every terminator BlockCall to block B passes exactly `B.params.len()` arguments, and each argument's `IRType`/`ValueRepresentation` is a subtype of / equals the corresponding parameter's. | Fatal |
| V5 | **Type consistency**: each operand's `IRType` is a subtype of the opcode's declared input type for that slot. | Error |
| V6 | **Terminator well-formedness**: every block ends in exactly one terminator (TERMINATOR flag), no non-terminator carries `targets`, and no instruction follows a terminator. The entry block has no predecessors and its parameters are the function parameters. | Fatal |
| V7 | **Effect ordering**: within a block, EFFECTFUL instructions retain a total program order; no EFFECTFUL instruction has been reordered past another it may alias (checked against the alias model). Pure instructions are unconstrained. | Error |
| V8 | **Guard/FrameState well-formedness**: every GUARD-flagged (and every deoptimising) instruction has a `frame_state`; the referenced `FrameState` passes the §4.10 R4.64 checks (slot counts match the source `bcp`, all named values dominate, no cyclic remat). | Error |
| V9 | **Source position**: every instruction/param has a non-default `SourcePosition`. | Warning |
| V10 | **CFG reducibility**: the CFG is reducible (every loop has a single header dominating its body); all successor blocks exist. | Fatal |

### 4.3.8.2 Pseudocode

```text
function verify(f: Function) → Vec<VerifyError>:
    errors = []
    dom = f.dominators()          // Cooper–Harvey–Kennedy over the CFG
    for block in f.layout.blocks():
        assert exactly one terminator, last in the block        // V6
        for inst in block.insts():
            check handles live (V1), use/pred maps (V2)
            for arg in inst.args:  check dom.dominates(def(arg), inst)   // V3
            check operand types ⊆ schema (V5)
            if inst is terminator:
                for call in inst.targets:
                    check call.args.len() == f.block(call.block).params.len()  // V4
                    check arg/param type+repr agreement                        // V4
            if inst.flags.GUARD: check frame_state present & valid (V8)
        check EFFECTFUL program order vs alias model            // V7
    check CFG reducible; all succs exist                        // V10
    return errors
```

### 4.3.8.3 Error Handling

- **Fatal** — panic in debug; in release, log + abort this function's compilation
  and fall back to the interpreter.
- **Error** — log; mark the function unoptimisable (stays at baseline, §4.4).
- **Warning** — log only; compilation continues.

## 4.3.9 Serialisation & Pretty-Printing

### 4.3.9.1 Text Format

Stable text format for debugging and golden tests, block-structured:

```text
function MY-FUNCTION(v0: Fixnum, v1: Fixnum) -> Fixnum {
block0(v0: Fixnum, v1: Fixnum):                 ;; @file.lisp:10:0
    v2 = FixnumAdd v0, v1 : Fixnum              ;; @file.lisp:11:3
    return v2                                   ;; @file.lisp:11:3
}
```

Format per instruction:
`v<r> = <Opcode>(<aux>)? <args>? (: <Type>)? (reason=… frame_state=fs<id>)?  ;; @<src>`.
Terminators print their targets as `block<id>(<args…>)`.

### 4.3.9.2 Binary Serialisation

For IR caching across sessions the function MAY be serialised: magic (`BSIR`, 4
bytes), version (2), block count (4), value count (4); then per block its
parameters and instruction list (opcode u16, type 4, flags 2, arg-count u8 + args
5×N, target list, aux, packed source_pos 8, optional frame_state id); followed by
the length-prefixed frame-state table and source map. Binary IR is NOT a stable
ABI; the version MUST be bumped on any layout change and readers MUST reject
unknown versions.

## 4.3.10 Concurrency & Configuration

IR functions are single-owner, single-writer: a `Function` belongs to the
compilation thread that created it and MUST NOT be shared across threads. Inlining
clones the callee's `Function` into the caller's, remapping handles and prefixing
the callee's `SourcePosition.inlined_at` chain.

| Knob | Default | Description |
|------|---------|-------------|
| `EGCL_VERIFY_IR` | `true` in debug, `false` in release | Run A4.07 after every pass |
| `EGCL_IR_DUMP` | `false` | Dump text IR to stderr after each pass |
| `EGCL_IR_DUMP_FILTER` | `*` | Glob filter for function names to dump |
| `EGCL_IR_CACHE` | `false` | Enable binary serialisation cache |
