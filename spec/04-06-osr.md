# §4.6 On-Stack Replacement & Deoptimisation

## 4.6.0 Scope

This section specifies the mechanisms by which Bliss transitions
executing code **upward** (OSR entry — from T0/T1 into T2 optimised
code at a loop back-edge) and **downward** (deoptimisation — from T2
back to the interpreter or baseline code when speculative optimisations
are invalidated). Both directions require capturing or reconstructing the full frame state
so that program semantics are preserved. Interacts with GC (§3),
profiling (§4.9), and stack layout (§2).

---

## 4.6.1 Requirements

| ID | Requirement | Level |
|----|-------------|-------|
| R4.38 | The runtime MUST support on-stack replacement from T0 or T1 into T2 at any counted back-edge while preserving all live local variables, the dynamic environment (special bindings, catch tags, unwind-protect frames), and the program counter. | MUST |
| R4.39 | The runtime MUST support deoptimisation from T2 back to T0 (interpreter) at any GC safepoint, restoring a semantically equivalent interpreter frame within one safepoint poll interval. | MUST |
| R4.40 | A per-function **deopt log** (D4.10) MUST record each deoptimisation event with its reason, and the runtime MUST blacklist a function from T2 promotion after exceeding a configurable deopt threshold. | MUST |
| R4.41 | OSR entry and deoptimisation MUST be safe with respect to concurrent GC; specifically, the transitioning thread MUST reach a safepoint before modifying its stack layout, and the new frame MUST be walkable by the GC before the thread resumes execution. | MUST |

## 4.6.2 Data Structures

### D4.09 — OSR Entry Map

The **OSR entry map** is a per-loop-header data structure emitted by the
T2 compiler. It describes how to transfer execution from the source tier
(T0 interpreter or T1 baseline code) into the middle of a T2-compiled
function at a specific loop header.

```rust
/// One entry map is generated per OSR-eligible back-edge target
/// (loop header) during T2 compilation.
struct OsrEntryMap {
    /// Byte-code or T1 instruction offset of the loop header.
    source_pc: u32,

    /// Native-code address of the T2 loop header entry stub.
    target_entry_addr: *const u8,

    /// Number of slots that must be transferred.
    slot_count: u16,

    /// Per-slot descriptors: how to populate the T2 frame from the
    /// source frame.
    slots: [OsrSlotDesc; /* slot_count */],

    /// Bitmap: which T2 SSA values are live at the entry point.
    /// Used by the GC to identify roots in the partially-initialised
    /// T2 frame.
    live_ref_bitmap: BitVec,

    /// Expected types for speculative type guards at OSR entry.
    /// If any guard fails, the OSR attempt is abandoned (not a deopt).
    type_guards: Vec<TypeGuard>,
}

struct OsrSlotDesc {
    /// Source location: stack offset in the T0/T1 frame.
    source_offset: i32,

    /// Destination: register or stack offset in the T2 frame.
    dest: Location,

    /// Representation conversion needed (e.g. boxed → unboxed fixnum).
    conversion: ConversionKind,
}

enum Location {
    Register(PhysReg),
    StackOffset(i32),
    FpRegister(FpReg),
}

enum ConversionKind {
    None,
    UnboxFixnum,
    UnboxFloat,
    BoxFixnum,
    BoxFloat,
    WidenI32ToI64,
}

struct TypeGuard {
    slot_index: u16,
    expected_tag: TypeTag,
}
```

**Invariants:**

1. `slot_count` MUST equal the number of live locals at the loop header
   in the source tier frame.
2. Every GC-reference slot in `dest` MUST have its corresponding bit set
   in `live_ref_bitmap`.
3. The `target_entry_addr` MUST point to a T2 stub that begins with a
   safepoint poll (§4.6.7).

### D4.10 — Deopt Log

The **deopt log** is a per-`CompiledFunction` ring buffer that records
recent deoptimisation events. It drives the blacklisting / backoff
policy.

```rust
struct DeoptLog {
    /// Circular buffer of recent deopt events.
    entries: RingBuffer<DeoptEntry, DEOPT_LOG_CAP>,

    /// Total lifetime deopt count for this function.
    total_deopts: u32,

    /// If true, T2 promotion is permanently suppressed.
    blacklisted: bool,

    /// Timestamp (monotonic tick) after which T2 re-promotion is
    /// allowed. Zero means no active backoff.
    backoff_until: u64,
}

struct DeoptEntry {
    /// Monotonic tick of the event.
    timestamp: u64,

    /// T2 native PC where the uncommon trap fired.
    trap_pc: *const u8,

    /// Reason category.
    reason: DeoptReason,

    /// The bytecode / T0 PC to which execution was transferred.
    resume_pc: u32,
}

/// Categories of deoptimisation.  Used for per-reason counters and
/// targeted re-compilation strategies.
enum DeoptReason {
    /// Type profile mismatch (e.g., expected fixnum, got bignum).
    TypeGuardFailure,
    /// Null / unbound variable check failed.
    NullCheck,
    /// Class / structure redefinition invalidated inlined layout.
    ClassRedefinition,
    /// Inlined callee was redefined (`setf fdefinition`).
    FunctionRedefinition,
    /// Arithmetic overflow on unboxed path.
    Overflow,
    /// Array bounds check on speculative elimination.
    BoundsCheck,
    /// Uncommon branch taken (cold path profiled never-taken).
    UncommonTrap,
    /// Division by zero on unboxed integer path.
    DivisionByZero,
    /// Explicit deoptimise intrinsic (compiler testing).
    Explicit,
}
```

**Invariants:**

1. `DEOPT_LOG_CAP` defaults to 32 entries (configurable, §4.6.8).
2. `total_deopts` is atomically incremented; reads MAY be relaxed.
3. `blacklisted` is set under the function's metadata lock and is
   visible to the tier-promotion logic (§4.9).

## 4.6.3 Algorithm A4.03 — OSR Entry

OSR entry is triggered when a back-edge counter in T0 or T1 code
exceeds the T2 promotion threshold and a compiled T2 version with a
matching `OsrEntryMap` is available (or has just completed compilation).

```text
ALGORITHM A4.03: OSR-ENTRY(frame, back_edge_pc)
────────────────────────────────────────────────

Input:
  frame          — current T0 or T1 stack frame
  back_edge_pc   — bytecode / T1 offset of the back-edge

Output:
  Execution continues in T2 code at the loop header, or
  the attempt is abandoned and T0/T1 execution continues.

Steps:

 1. LOOKUP compiled T2 function for frame.function.
    IF not yet compiled:
      a. Enqueue an async T2 compilation request (§4.4).
      b. RETURN (continue in current tier).

 2. LOOKUP OsrEntryMap for back_edge_pc in the T2 metadata.
    IF no entry map exists for this PC:
      RETURN (this loop header is not OSR-eligible).

 3. SAFEPOINT-POLL:
    Enter a GC safepoint (§3).  This ensures:
      a. No GC is in progress that would see a half-built frame.
      b. The thread is in a consistent state for stack modification.

 4. TYPE-GUARD CHECK:
    FOR EACH guard IN entry_map.type_guards:
      val ← read source frame slot[guard.slot_index]
      IF tag_of(val) ≠ guard.expected_tag:
        Record OSR_GUARD_FAILURE in profiling counters.
        LEAVE safepoint.
        RETURN (continue in current tier; do NOT deopt).

 5. ALLOCATE T2 FRAME:
    new_frame ← allocate stack frame of T2 function's frame size.
    Mark new_frame as NOT YET WALKABLE in the stack-map metadata.

 6. TRANSFER STATE:
    FOR EACH slot_desc IN entry_map.slots:
      src_val ← read frame at slot_desc.source_offset
      IF slot_desc.conversion ≠ None:
        src_val ← apply_conversion(src_val, slot_desc.conversion)
      write new_frame at slot_desc.dest ← src_val

 7. COPY DYNAMIC ENVIRONMENT:
    Copy the dynamic binding stack pointer, catch-tag chain,
    and unwind-protect chain from frame to new_frame's reserved
    slots.  These are at fixed offsets defined by §2 stack layout.

 8. SET RETURN ADDRESS:
    new_frame.return_addr ← frame.return_addr
    (The T2 function returns to the same caller as the T0/T1 frame.)

 9. INSTALL STACK MAP:
    Register entry_map.live_ref_bitmap as the GC stack map for
    new_frame at the entry PC.
    Mark new_frame as WALKABLE.

10. WAIT-FOR-GC-SCAN-COMPLETE:
    IF a GC cycle is in progress AND has not yet finished scanning
    this thread's stack:
      Block until the GC completes stack-scanning for this thread.
    (This ensures the GC has finished reading the old frame before
     it is unlinked.  See §4.6.7.2.)

11. REMOVE OLD FRAME:
    Unlink frame from the stack chain.
    (The T0/T1 frame's slots become dead; GC will not scan them.)

12. LEAVE SAFEPOINT.

13. JUMP to entry_map.target_entry_addr.
    Execution continues in T2 code.
```

**Complexity:** O(S) where S = `slot_count` (typically < 64).

**Error handling:**
- If `allocate stack frame` fails (stack overflow), signal a
  `STORAGE-CONDITION` via the condition system rather than crashing.
- Type guard failures are NOT errors; they simply abandon the OSR
  attempt. The profiling subsystem MAY adaptively raise the back-edge
  threshold for that loop.

## 4.6.4 Algorithm A4.04 — Deoptimisation

Deoptimisation transfers execution from T2 optimised code back to the
T0 interpreter when a speculative assumption is violated.

```text
ALGORITHM A4.04: DEOPT(trap_pc, t2_frame, reason)
──────────────────────────────────────────────────

Input:
  trap_pc    — native PC of the uncommon trap instruction
  t2_frame   — current T2 stack frame
  reason     — DeoptReason enum value

Output:
  Execution resumes in the T0 interpreter at the corresponding
  bytecode PC with a reconstructed interpreter frame.

Steps:

 1. LOOKUP GC STACK MAP for trap_pc.
    The stack map encodes:
      a. Which frame slots / registers hold live SSA values.
      b. The bytecode PC to resume at (resume_pc).
      c. The unboxing state of each value (was it unboxed?).
    IF no stack map found:
      PANIC — this is a compiler bug (every trap site MUST have a map).

 2. SAFEPOINT-ENTER:
    Enter a GC safepoint.  The T2 frame is still walkable using
    the stack map obtained in step 1.

 3. CAPTURE SSA VALUES:
    live_values ← empty map
    FOR EACH entry IN stack_map.live_entries:
      raw ← read t2_frame at entry.location  (register or stack)
      IF entry.needs_boxing:
        raw ← box_value(raw, entry.type_tag)
      live_values[entry.bytecode_local_index] ← raw

 4. CAPTURE DYNAMIC ENVIRONMENT:
    Save special-binding stack depth, catch-tag chain head, and
    unwind-protect chain head from t2_frame's reserved slots.

 5. ALLOCATE INTERPRETER FRAME:
    interp_frame ← allocate T0 interpreter frame with
      - function = t2_frame.function
      - num_locals = function.num_locals
      - pc = resume_pc (from stack map)
    Mark interp_frame as NOT YET WALKABLE.

 6. POPULATE INTERPRETER FRAME:
    FOR EACH (idx, val) IN live_values:
      interp_frame.locals[idx] ← val
    FOR EACH local NOT IN live_values:
      interp_frame.locals[local] ← UNBOUND-MARKER
      (Dead values in T2 may correspond to live-but-unused locals
       in the interpreter.  The interpreter will signal an error
       if they are referenced, which matches correct CL semantics.)

    NOTE — INLINING SCOPE: Bliss T2 performs inlining at the IR level
    but does NOT inline across logical frame boundaries.  Every inlined
    callee is represented within the T2 frame as a region of the same
    SSA graph; no separate interpreter frame exists for it.  Therefore
    deoptimisation always reconstructs exactly ONE interpreter frame —
    the outermost function.  Inlined callees are effectively "un-inlined"
    by the resume-PC mapping back to the caller's bytecode position.
    If a future version introduces frame-level callee inlining (virtual
    frames), this algorithm MUST be extended to reconstruct a chain of
    interpreter frames analogous to HotSpot's virtual-frame mechanism.

 7. RESTORE DYNAMIC ENVIRONMENT:
    Set interp_frame's special-binding depth, catch-tag chain,
    and unwind-protect chain to the values saved in step 4.

 8. SET RETURN ADDRESS:
    interp_frame.return_addr ← t2_frame.return_addr

 9. INSTALL INTERPRETER STACK MAP:
    Register the standard interpreter frame map (all locals are
    tagged BlissVals → all are GC roots).
    Mark interp_frame as WALKABLE.

10. WAIT-FOR-GC-SCAN-COMPLETE:
    IF a GC cycle is in progress AND has not yet finished scanning
    this thread's stack:
      Block until the GC completes stack-scanning for this thread.
    (This ensures the GC has finished reading the T2 frame before
     it is unlinked.  See §4.6.7.2.)

11. REMOVE T2 FRAME:
    Unlink t2_frame from the stack chain.

12. LOG DEOPT EVENT:
    entry ← DeoptEntry {
      timestamp: monotonic_tick(),
      trap_pc: trap_pc,
      reason: reason,
      resume_pc: resume_pc,
    }
    function.deopt_log.push(entry)
    function.deopt_log.total_deopts += 1  (atomic)

13. EVALUATE BLACKLISTING (see §4.6.5):
    apply_backoff_policy(function.deopt_log)

14. LEAVE SAFEPOINT.

15. JUMP to interpreter loop entry with interp_frame.
    The interpreter reads interp_frame.pc and resumes execution.
```

**Complexity:** O(L) where L = number of live locals (typically < 128).

**Error handling:**
- Step 1 panic indicates a compiler invariant violation. In debug builds
  the panic includes the trap PC and function name.
- Stack overflow during interpreter frame allocation triggers
  `STORAGE-CONDITION`.

## 4.6.5 Deopt Log, Blacklisting & Backoff Policy

The deopt log (D4.10) drives adaptive recompilation policy. The
subsystem prevents "deopt storms" where a function repeatedly promotes
to T2 and immediately deopts.

### 4.6.5.1 Per-Reason Counters

The runtime maintains per-reason counters derived from the deopt log
ring buffer. When evaluating whether to re-promote, the counters for
the most recent `DEOPT_WINDOW` ticks (default: 10 000 ticks) are
examined.

### 4.6.5.2 Backoff Schedule

| Condition | Action |
|-----------|--------|
| 1st deopt for a given reason | No action; T2 code remains active (if other paths are still valid). Re-promote on next threshold hit. |
| 2nd deopt for same reason within window | Exponential backoff: suppress T2 promotion for `BACKOFF_BASE × 2^(count−2)` ticks. Default `BACKOFF_BASE` = 500 ticks. |
| `total_deopts` ≥ `BLACKLIST_THRESHOLD` | Permanently blacklist: set `deopt_log.blacklisted = true`. Function remains at T1 (or T0 if T1 also problematic). Default `BLACKLIST_THRESHOLD` = 20. |

### 4.6.5.3 Blacklist Reset

A blacklisted function MAY be un-blacklisted by:

1. **Class/function redefinition:** If the deopt reasons were
   `ClassRedefinition` or `FunctionRedefinition`, redefining the
   relevant class or function clears the blacklist (the assumptions
   that caused deopts may now hold).
2. **Explicit user request:** `(bliss-ext:reset-deopt-log fn)` clears
   the log and removes the blacklist flag.
3. **Image reload:** Deopt logs are NOT persisted across image
   save/load (§7).

## 4.6.6 Uncommon Trap Encoding

T2 compiled code encodes deoptimisation points as **uncommon traps** —
lightweight instructions that transfer control to the deopt handler.

### 4.6.6.1 Trap Instruction

On x86-64, uncommon traps use `ud2` (undefined instruction), which
generates SIGILL. On AArch64, `brk #DEOPT_IMM` is used. Both are
two-byte instructions that minimise I-cache footprint in cold paths.

### 4.6.6.2 Trap Metadata Table

A side-table in the compiled function's metadata maps each trap PC to:

| Field | Type | Description |
|-------|------|-------------|
| `trap_pc` | `u32` (offset from function base) | Address of the trap instruction |
| `stack_map_index` | `u16` | Index into the function's GC stack map array |
| `reason` | `DeoptReason` | Why this trap exists |
| `resume_pc` | `u32` | Bytecode PC for interpreter resumption |

The signal handler (§2) intercepts the trap signal, looks up the
trap PC in the metadata table, and dispatches to Algorithm A4.04.

## 4.6.7 GC Safepoint Interaction During OSR

Both OSR entry and deoptimisation modify the stack in ways that
temporarily invalidate the GC's ability to walk it.  The following
protocol ensures safety:

### 4.6.7.1 Safepoint Protocol

1. **Enter safepoint** — the thread announces it is at a safepoint,
   allowing a concurrent GC cycle to proceed if pending. The OLD frame
   is still on the stack and is walkable.
2. **Build new frame** — the new frame is allocated and populated.
   During this window, the new frame is marked NOT WALKABLE in the
   frame chain metadata.
3. **Install stack map** — the new frame's GC stack map is registered.
   The new frame is marked WALKABLE.
4. **Wait for GC scan complete** — if a GC cycle is in progress and
   has not yet finished scanning this thread's stack, the thread blocks
   until stack-scanning completes. This ensures the GC has finished
   reading the old frame before it is removed.
5. **Remove old frame** — the old frame is unlinked. Only one walkable
   frame exists for this activation at any time.
6. **Leave safepoint** — the thread resumes normal execution.

### 4.6.7.2 Concurrent GC Visibility

If a GC cycle begins while a thread is between steps 2 and 4, the GC
sees the OLD frame (still linked and walkable) and scans its roots; the
new frame is invisible. The thread blocks at the safepoint until the GC
completes stack-scanning, then continues with steps 3–5. The GC never
encounters a half-built frame and never misses roots.

## 4.6.8 Configuration

| Knob | Type | Default | Description |
|------|------|---------|-------------|
| `BLISS_OSR_BACKEDGE_THRESHOLD` | `u32` | 5000 | Back-edge count to trigger T2 compilation + OSR |
| `BLISS_DEOPT_LOG_CAP` | `u16` | 32 | Ring buffer capacity per function |
| `BLISS_BLACKLIST_THRESHOLD` | `u16` | 20 | Lifetime deopt count to blacklist a function |
| `BLISS_BACKOFF_BASE` | `u64` | 500 | Base backoff period in monotonic ticks |
| `BLISS_DEOPT_WINDOW` | `u64` | 10000 | Sliding window (ticks) for per-reason counters |
| `BLISS_OSR_ENABLED` | `bool` | `true` | Master switch; `false` disables all OSR |

All knobs are settable via environment variables and via
`(bliss-ext:set-runtime-option :osr-backedge-threshold 10000)`.

## 4.6.9 Error Handling

| Failure Mode | Detection | Recovery |
|--------------|-----------|----------|
| No stack map at trap PC | Assertion in deopt handler (step 1 of A4.04) | Panic with diagnostic — compiler bug |
| Stack overflow during frame allocation | Guard page hit | Signal `STORAGE-CONDITION` to the CL condition system |
| Type guard failure at OSR entry | Step 4 of A4.03 | Abandon OSR; continue in current tier |
| Corrupt deopt log (e.g., torn write) | CRC or sequence-number check on ring buffer | Reset log, increment a global `deopt_log_reset` counter |
| OSR entry map version mismatch (stale T1 → new T2) | Version counter in `CompiledFunction` checked at step 2 of A4.03 | Abandon OSR; background recompile with fresh profile |

## 4.6.10 Concurrency

- **Deopt log mutation** is lock-free: `total_deopts` uses
  `AtomicU32::fetch_add(Relaxed)`; ring buffer writes use a CAS on the
  write index. The log is single-writer (only the thread that owns the
  frame writes) but may be read by the profiling thread (§4.9).
- **Blacklist flag** is set under `CompiledFunction.meta_lock`
  (a lightweight spinlock) because it requires a compare-and-swap on
  `backoff_until` and `blacklisted` together.
- **OSR entry** and **deopt** are always performed by the executing
  thread on its own stack. No cross-thread stack modification occurs.
- **Stack map tables** are immutable once emitted by the compiler and
  are safe to read concurrently from any thread (e.g., GC stack walker).

## 4.6.11 Test Strategy

| Test | Scope | Method |
|------|-------|--------|
| OSR entry round-trip | Unit | Compile a hot loop, verify T2 entry occurs and results are correct |
| Deopt on type change | Unit | Optimise with fixnum profile, inject a bignum, verify deopt + correct result |
| Blacklisting | Unit | Force > `BLACKLIST_THRESHOLD` deopts, verify function stays at T1 |
| Backoff timing | Unit | Verify exponential backoff schedule via mock tick source |
| GC during OSR | Integration | Trigger GC safepoint in mid-OSR, verify no crash and roots scanned |
| Dynamic env preservation | Integration | Verify `*special-var*` bindings, catch tags, and unwind-protect survive OSR/deopt |
| Multi-threaded OSR | Stress | Multiple threads entering OSR concurrently on the same function |
| Deopt log overflow | Unit | Push > `DEOPT_LOG_CAP` entries, verify ring wraps correctly |
| Version mismatch guard | Unit | Redefine function between T1 counter hit and OSR attempt |
| Stack overflow during OSR | Unit | Near-limit stack, attempt OSR, verify `STORAGE-CONDITION` signalled |
| Blacklist cleared on redefinition | Unit | Blacklist a function via repeated deopts with `ClassRedefinition` reason, redefine the class, verify `blacklisted` is cleared and T2 re-promotion is permitted |
| Explicit deopt-log reset | Unit | Blacklist a function, call `(bliss-ext:reset-deopt-log fn)`, verify `blacklisted` is `false`, `total_deopts` is 0, and ring buffer is empty |
| Deopt log not persisted across image | Integration | Blacklist a function, save image via `(bliss-ext:save-image ...)`, reload image, verify deopt log is fresh (empty, not blacklisted) |
