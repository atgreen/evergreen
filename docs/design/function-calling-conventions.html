EGCL · an implementation guide

How a function call travels
through the four execution tiers

A function call must deliver arguments, remember where to return, and keep live objects safe. EGCL does this in several ways, depending on how the caller and callee execute.

1. Four ways to run the same Lisp function

In (f 10 20), the code evaluating that expression is the caller; f is the callee. Each may run at a different tier. A higher tier changes how the body executes, while preserving the Lisp meaning.

TierWhat executes?Where to start reading
Tree walkerRust code walks Lisp forms such as IF and function calls directly.cli.rs: eval_form, eval_list, apply_function_impl
T0A Rust loop interprets bytecode: a simpler sequence of instructions with locals and an operand stack.cli/bytecode.rs: run_with_binding, run_loop
T1Baseline native machine code. Compilation aims to get execution out of the interpreter quickly.native_transfer_entry.rs and the baseline emitters
T2Optimized native machine code. It may rely on checked assumptions and return to T0 when one fails.egcl-compiler/src/t2/

A calling convention (part of an ABI, or application binary interface) is the agreement at a function's entrance and exit: where arguments go, what a return looks like, and which registers must survive. A register is a small, fast storage location inside the CPU. A stack frame is storage belonging to one active call. Metadata describes that storage so the runtime can inspect it.

Tier and calling convention are different choices. Eligible T1 and T2 bodies share the ordinary native convention. Other bodies use compatible mapped or legacy entries. Even an interpreted body can sit behind a native adapter. A native-looking entrance does not prove the body runs natively.

3. Native → native: a five-argument example

Imagine (f a b c d e) calling an eligible environment-free T1 or T2 body. The first three values go into CPU registers; the remaining two go on the machine stack. Every argument is a 64-bit EgclVal: a tagged word that represents a Lisp value. A small integer may fit directly in that word; a heap object is reached through a tagged pointer.

The supplied count excludes the closure and context. For a closure entry, RAX holds the tagged callable/closure object instead of NIL. This lets an adapter find captured variables. It does not mean every closure body has ordinary native code.

The caller rounds overflow-argument storage up to a multiple of 16 bytes and aligns RSP before CALL. With five arguments, two overflow words use 16 bytes. With four arguments, the one overflow word is followed by eight bytes of padding. Padding follows the arguments and is not a Lisp value. CALL pushes an eight-byte return address, so entry RSP is eight bytes off a 16-byte boundary.

Register groupWhat survives a call?
RAX RCX RDX RDI RSI R8 R9 R10 R11Caller-clobbered: the caller must save any value it still needs. Some carry the result at return.
RBX R12 R14 R15 RBPCallee-preserved: if used, their incoming state must be saved and restored. Backend reservations still apply; “preserved” does not mean freely allocatable everywhere.
R13Preserved execution-context pointer, shared by ordinary calls within the execution.
XMM0–XMM15No baseline tagged Lisp argument role; caller-clobbered. Specialized numeric paths have separate rules.

The stack grows toward lower addresses. RBP provides a frame-chain anchor; RSP moves as storage is reserved. A spill is a value temporarily stored in memory instead of a register. Before a nested call, the caller prepares a separate outgoing argument area. That area is callee-clobberable: a value needed later must also have a surviving home.

Named calls use a stable CallCell. Its ordinary-entry slot selects a retained OrdinaryEntryDescriptor: ABI kind/version, definition revision, entry address, code range, arity, environment kind, owner, and required stack space. Publication validates the immutable ABI kind/version and code-owner information; generated calls check the selected descriptor, definition revision, arity/environment, and stack/poll admission. They do not treat any machine address as callable. Eligible source-proven self-calls can use their own retained entry directly; dynamic calls must respect redefinition.

No managed child frame is eagerly created for each eligible ordinary native call. The native machine frame and its separately retained maps carry the state. An outer native segment provides a runtime boundary around a run of native calls.

The frame diagram shows an ordinary CALL. Some eligible forwarding tail calls instead retire the current frame and jump to the target, reusing the original return address. The arguments must fit the existing incoming overflow capacity, and no pending control obligation may require the frame; otherwise the path falls back to a call and return.

4. T0 and the tree walker: no fixed Lisp argument registers

Both engines are implemented in Rust. Rust's compiler chooses their internal machine registers. Their stable, useful layouts are the runtime data structures below—not an imagined set of T0 or tree-walker CPU registers.

T0 keeps values and execution bookkeeping separately

T0's operand stack holds intermediate expression results. A registered named T0 → T0 call takes evaluated arguments from the caller's operands, roots them, creates and binds a callee frame, and pushes an Activation record. The same run_loop then executes the callee. On return it pops the callee and pushes the primary result onto the caller's operand stack.

The managed header is 40 bytes. Its num_locals field counts the reserved frame slots, despite its name; T0's Activation.n_locals separates actual locals from operands. The managed header's return_pc is not T0's live instruction cursor: Activation.bcp tracks bytecode progress. A generic call can leave the flat T0 loop and use callable dispatch.

The tree walker binds a lexical environment

The tree walker first evaluates argument expressions, then binds their values to parameters in a child EnvFrame. A lexical environment is the set of variable bindings visible at that place in the source. Closures retain a captured environment and lexical control information. Evaluating the body recursively uses Rust calls, rooted temporary argument storage, and environment structures.

Local source-body calls can enter eval_named_call_ex directly. Function-object calls normally go through apply_function. On x86-64 Linux that wrapper enters an ordinary callable adapter before apply_function_impl selects the body. Therefore even a tree → tree call may cross a native assembly boundary while still evaluating both bodies as source.

5. Crossing between native and interpreted code

An adapter translates one entry convention into another. It also establishes roots and a safe error boundary. It is more than a few register moves.

Interpreted caller → native callee

T0's native branch uses run_native_callable. Tree-call dispatch uses call_registered when compiled code exists. The selected native code chooses a suitable entry. The ordinary bridge marshals the arguments into the register/overflow layout. Compatible mapped paths can import activation state; the legacy checked path explicitly builds an EgclStack frame and binds its slots before entering machine code.

Native caller → interpreted callee

An ordinary named-call veneer reaches ordinary_calls::named_entry, which publishes native roots, roots all supplied arguments and the closure, copies arguments into a rooted buffer, polls the runtime, and calls call_table::ordinary_call. A bytecode target uses the T0 runner; a function-object target uses callable dispatch. The callable-object veneer similarly reaches apply_function_impl.

A veneer is a small assembly adapter. A poll is a controlled point where execution checks for work such as collection, signals, or yielding. The veneer cannot assume an incorrect argument count is safe: even an arity-error path must protect all supplied values before an allocating helper runs.

When interpreted work finishes, the adapter translates Result<EgclVal, EgclError> and the environment's multiple-value state into the native outcome. Rust helper frames finish before assembly performs a non-local native transfer.

6. Coming back: one, zero, or many values

Common Lisp functions can return more than one value. For example, (values 10 20) returns two; (values) returns zero. In a context that asks only for the primary value, zero values behave as NIL.

Ordinary native returnCarry flag (CF)RAXRDXRCX
Exactly one value0 (clear)The valueUnspecifiedUnspecified
Zero values1 (set)NIL0Null pointer
Two or more values1 (set)Primary valueFull value countPointer to complete tuple, including primary

The carry flag is one bit in the CPU's status flags. Here it distinguishes a single value from zero/many values; it does not mean “error.” Cleanup must preserve that bit and the meaningful result registers. This is why ordinary epilogues can use LEA to adjust the stack without changing flags.

T0 and the tree walker carry the primary result directly and keep additional-value state in Env.mv and mv_active. In T0 the primary also enters the caller's operand stack. Adapters normalize this into the native descriptor: single returns leave the buffer inactive; zero returns have an active empty buffer; many returns have an active full tuple. A caller that needs values after another call must copy them into traced storage first.

Ordinary native bodies do not yet support every multiple-value consumer. Some can forward a callee's whole return unchanged; more complex contexts retain a compatible execution path.

7. Why the maps matter: objects can move

EGCL has a moving garbage collector. If a live object moves from address A to B, every reference that execution will use must be updated. A root is a location the collector knows contains a live Lisp value. A raw address that the collector does not know about can become stale.

For native code, “the value is in RBX” is not enough. A callee may have saved the caller's RBX on its own stack and reused the register. The runtime combines each frame's exact-PC value map with the unwind recipe—the instructions for finding saved registers and the previous frame—to find the authoritative, writable copy.

The code owner remains retained while an active or suspended segment could still refer to it, even if the function is redefined. The machine frame does not contain a copy of all these tables. Its return address connects it to the retained metadata.

T0's managed slots and rooted activation records provide its roots. Tree evaluation roots its temporary values and environments. Legacy T2 paths can copy live values into shadow root slots appended to an EgclStack activation, then reload after an allocating call. Fully published native paths can instead describe native stack/register homes directly. These are distinct mechanisms; not every native frame has shadow slots.

8. Other entries you will encounter in the source

The ordinary convention is the main x86-64 Linux route for supported tagged T1/T2 bodies. The repository also contains these entry families. Never substitute one entry address for another merely because both belong to the same function.

Legacy c2i helpers mean “compiled to interpreter/runtime.” Small checked calls can pass a symbol, count, and up to three values in host-ABI registers; wider calls use a rooted argument slice. The checked path records errors in NATIVE_ERROR, returns a placeholder, and relies on generated checks. Ordinary native segment transfers use their explicit outcome/landing machinery instead. A C helper's flags are not a Lisp return descriptor.

Optimization failure is a continuation, not a fresh call

Deoptimization happens when a compiled assumption fails. T2's frame-state metadata describes the bytecode position, locals, and operand stack needed to resume in T0. After side effects, recovery must resume at the correct continuation rather than restart and repeat completed calls. This is distinct from selecting T0 as the callee at a normal call boundary.

Errors and non-local exits

A normal return goes back to the immediate caller. Lisp THROW, RETURN-FROM, and error handling may leave several calls, running cleanups and restoring dynamic bindings along the way. T0 uses explicit handler/unwind bookkeeping; the tree evaluator propagates Rust results; native mapped/segment paths use recorded transfer sites and cold landings. They must not jump across still-live Rust helper frames.

Current limits

The general ordinary native body emitter admits a subset: tagged values, fixed parameters, supported operations and control flow. Captured environments, variadic native bodies, protected control regions, raw numeric representations, and some frame-state shapes require other paths. Ordinary adapters can still handle closures, optional/rest binding, generic functions, or interpreted bodies. The current build stage is 5; the broader Stage 6 ABI specification is not evidence that every target requirement is implemented.

Other architectures and Windows have their own native adapters, including mapped-transfer implementations. This document deliberately does not assign x86 registers to those platforms. The all-tier matrix describes semantic routes; the physical diagrams describe x86-64 Linux.

9. A short reading route through the source

Start with the interpreter dispatch, then follow one native entry. The very large bytecode.rs contains both T0 execution and native integration; its name does not mean everything inside runs as bytecode.

  1. apply_function → apply_function_impl — How a function object is selected and executed.
  2. T0 CallNamed — How arguments leave the operand stack and a destination is selected.
  3. ordinary_call — How stable call-table linkage chooses bytecode, native code, or a function object.
  4. ordinary machine entry — Where the register and overflow arguments become native value homes.
  5. native returns — The short assembly sequences encoding one or multiple values.
  6. native call maps — How return addresses connect frames to value and unwind metadata.
